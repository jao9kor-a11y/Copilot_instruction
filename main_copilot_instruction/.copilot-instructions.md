# Copilot Instructions for CAPL Script Generation from Test Cases

## Purpose
Generate CAPL (CAN Access Programming Language) script files (.can format) for automotive ECU testing based on UDS (Unified Diagnostic Services) test specifications from CSV test cases. These scripts run in Vector CANoe/CANalyzer.

## Input Format
CSV file with the following columns:
- `req_id`: Requirement identifier
- `fnid`: Function identifier
- `object_text`: Requirement description with DID specifications
- `verification_criteria`: Test verification criteria
- `test_purpose`: Purpose of the test
- `test_scenario`: Test scenario with input/output tables
- `test_precondition`: Prerequisites for test execution
- `test_execution`: Detailed step-by-step test execution with UDS commands

## Output Format: CAPL Script Structure

Generate .can files containing CAPL scripts with the following structure:

```capl
/*==============================================================================
  CAPL Script: <Testcase_Name>
  Requirement ID: <req_id>
  Function ID: <fnid>
  Purpose: <test_purpose>
  Preconditions: <test_precondition>
==============================================================================*/

includes
{
  // Add any required includes here
}

variables
{
  // Test variables
}

// Functions and event handlers
```

## CAPL Script Generation Rules

### 1. CAPL Syntax Requirements
- **NO array parameters in functions**: CAPL doesn't support `byte data[8]` as function parameters
- Use individual byte parameters: `byte b0, byte b1, byte b2, ...`
- **NO local array initialization**: Avoid `byte data[8] = {0x10, 0x01, ...}`
- Use individual assignments or pass bytes directly to functions
- **Timer handling**: Use `msTimer` for delays and test sequencing
- **Global variables**: Use global `testStep` variable instead of `static` in timer handlers

### 2. Message Timing in CAPL
- Use `setTimer(testTimer, milliseconds)` for delays
- Default delay between steps: `100` milliseconds
- Response timeout: `10` milliseconds
- Ex4. UDS Service Implementation in CAPL

#### Common UDS Services:
- **0x10**: DiagnosticSessionControl
  - `0x10 0x01`: Default Session
  - `0x10 0x02`: Programming Session
  - `0x10 0x03`: Extended Diagnostic Session
  
- **0x22**: ReadDataByIdentifier
  - Format: `0x22 <DID_High> <DID_Low>`
  - Example: `SendUDSRequest(0x22, 0xFE, 0xFC, 0x00, 0x00, 0x00, 0x00, 0x00, 3)`

- **0x27**: SecurityAccess
  - `0x27 0x01`: Request Seed (Bosch level)
  - `0x27 0x02`: Send Key
  - Implement seed-key exchange with proper timing

- **0x2E**: WriteDataByIdentifier
  - Format: `0x2E <DID_High> <DID_Low> <data_bytes>`

#### Positive Responses (Handle in `on message 0x748`):
- Response = Request Service ID + 0x40
- Example: Request `0x10` → Response `0x50`
- Example: Request `0x22` → Response `0x62`

#### Negative Responses:
- Format: `0x7F <Service_ID> <NRC>`
- Common NRCs:
  - `0x7E`: Sub-function Not Supported In Active Session
  - `0x7F`: Service Not Supported In Active Session
  - `0x33`: Security Access Denied
  - `0x31`: Request Out Of Range
  - `0x13`: Incorrect Message Length

### 5. CAPL Function Template: SendUDSRequest

**CRITICAL: Use individual byte parameters, NOT arrays**

```capl
void SendUDSRequest(byte b0, byte b1, byte b2, byte b3, byte b4, byte b5, byte b6, byte b7, int dlc)
{
  message 0x740 msg;
  
  msg.byte(0) = b0;
  msg.byte(1) = b1;
  msg.byte(2) = b2;
  msg.byte(3) = b3;
  msg.byte(4) = b4;
  msg.byte(5) = b5;
  msg.byte(6) = b6;
  msg.byte(7) = b7;
  msg.dlc = dlc;
  
  output(msg);
  write("Tx: 0x740 - %02X %02X %02X %02X %02X %02X %02X %02X", 
        b0, b1, b2, b3, b4, b5, b6, b7);
}
```

### 6. Message Padding
- Always send 8 bytes in CAPL messages
- Pad unused bytes with `0x00`
- Set `dlc` to actual data length (e.g., `dlc = 3` for 3-byte command)

### 7. Multi-Frame Messages (ISO-TP)
For messages > 7 bytes (implement if needed):
- Use Vector's DiagOnCAN library for automatic ISO-TP handling
- Or manually implement: First Frame, Flow Control, Consecutive Frames

## Error Prevention & Quality Assurance

### Common CAPL Errors to Avoid:
1. **Parse Error at Line XX**: Usually caused by array parameters or initialization
2. **Undefined Variable**: All variables must be declared in `variables` section
3. **Type Mismatch**: Ensure byte values are in range 0x00-0xFF
4. **Message Not Declared**: Use inline declaration `message 0x740 msg;`
5. **Incorrect Function Call**: SendUDSRequest needs exactly 9 parameters

### Auto-Validation Rules Applied:
- Extract only hex bytes from `[0xXX 0xYY ...]` format
- Count actual data bytes for dlc (exclude padding zeros)
- Pad all messages to 8 bytes automatically
- Convert timer delays: "60 seconds" → 60000 milliseconds
- Validate all hex values are 2-digit format: 0x01 not 0x1
- Ensure testStep starts at 1 and increments sequentially

### ✅ CAPL Generation Validation Checklist:
Before outputting CAPL script, automatically verify:
- [ ] SendUDSRequest function has exactly 9 parameters (8 bytes + 1 dlc)
- [ ] All SendUDSRequest calls pass exactly 9 arguments
- [ ] All hex values are valid: 0x00 to 0xFF format
- [ ] No array parameters in any function definitions
- [ ] No local array initialization with `= {...}` syntax
- [ ] All variables declared in `variables` section
- [ ] testStep is global variable, not static or local
- [ ] Timer delays are in milliseconds (integer values)
- [ ] dlc parameter matches actual data length
- [ ] All bytes padded to 8 with 0x00
- [ ] Message IDs are valid hex (0x740, 0x748)
- [ ] No undefined variables or messages referenced
- [ ] Message access uses `this.byte(n)` in event handlers

## Best Practices

1. **Preserve Test Context**: Include test purpose and preconditions as comments
2. **Clear Step Separation**: Add comments before each test step
3. **Realistic Timing**: Use timing that reflects real ECU response times
4. **Error Handling**: Include negative response cases where specified
5. **Readability**: Format hex data consistently (uppercase, space-separated)
6. **Validation**: Ensure all messages are 8 bytes (padded with 0x00)
7. **Channel Assignment**: Use channel 1 for standard tests unless specified otherwise

## DID Value Extraction
When object_text contains DID tables:
- Parse DID value (e.g., `FEFC`)
- Extract session requirements (Default, Extended, Programming)
- Extract security level requirements (None, Bosch, InCar1, etc.)
- Extract read/write access permissions

## Error Detection
Alert if:
- Request data or response data is missing from test execution
- Hex data is malformed or incomplete
- Test step references undefined DIDs or services
- Security level requirements are ambiguous
- Session requirements conflict with test steps
